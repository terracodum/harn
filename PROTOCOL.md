# Вход и результат генератора

Этот документ определяет внешний контракт программы. Способ реализации и внутренний процесс команда выбирает самостоятельно. Полный пример структуры кейса находится в [example-case/](example-case/).

## 1. Входные параметры

Пример: [inputs/settlement.json](inputs/settlement.json). Все перечисленные поля обязательны. Относительные пути отсчитываются от расположения входного JSON-файла.

- `protocol_version`: строка `"1.0"`.
- `repository`: путь к исходному репозиторию. Его содержимое нельзя изменять.
- `brief`: описание требуемого изменения и ограничений на естественном языке.
- `output_dir`: новая папка для результата. Существующие данные нельзя перезаписывать.
- `case_id`: идентификатор кейса в формате `команда/название`.
- `difficulty`: `easy`, `medium` или `hard`.
- `language`: язык задания, `ru` или `en`; это не язык программирования.
- `source`: идентификатор исходного задания.
- `team`: название команды.
- `author`: объект с непустыми строками `name` и `email`. В примере указаны вымышленные данные; перед сдачей укажите свои.
- `limits`: положительные значения `agent_timeout_sec`, `verifier_timeout_sec`, `build_timeout_sec`, `cpus`, `memory_mb`, `storage_mb`.
- `seed`: целое число для случайных процедур программы. Воспроизводимость ответов внешней LLM этим не гарантируется.

`agent_timeout_sec` — время на решение созданной задачи; `verifier_timeout_sec` — время её проверки; `build_timeout_sec` — время сборки окружения. Это лимиты кейса, а не бюджет генератора.

Интерфейс программы произвольный. В инструкции запуска объясните, как передать все эти параметры. При некорректном входе программа должна сообщить об ошибке.

## 2. Результат

В `output_dir`:

```text
task/                       # Сам кейс; структура описана ниже
evidence/                   # Доказательства выполненных проверок
  summary.json
  build.log
  base/
  oracle/
  llm_usage.json
result.json                 # Статус генерации
```

`result.json` содержит:

- `protocol_version`, `case_id` — значения из входа;
- `status` — `ready` при выполнении всех требований или `failed`;
- `task_path`, `evidence_path` — относительные пути от `output_dir` либо `null`, если соответствующие артефакты не созданы;
- `limitations` — массив строк с ограничениями или причинами неуспеха, пустой при их отсутствии;
- `input_snapshot_sha256` — SHA-256 исходного репозитория.

Для вычисления хэша снимка перечислите все обычные файлы репозитория, включая скрытые, по относительному POSIX-пути в лексикографическом порядке. Для каждого сформируйте строку `путь`, нулевой байт, SHA-256 содержимого в lowercase hex, перевод строки. Хэш снимка — SHA-256 объединённых строк в UTF-8. Символьные ссылки в исходном наборе не используются.

`summary.json` содержит массив `runs`: для каждого прогона — команды, версия окружения, длительность, код завершения, reward и путь к отчёту с исходом каждого теста. Прогоны, которые не выполнялись, не считаются успешными. В `base/` и `oracle/` сохраняются stdout/stderr и отчёты тестов; в `build.log` — вывод сборки. Здесь **base** означает исходный код, **oracle** — код после эталонного решения.

`llm_usage.json` содержит массив `calls`: модель, длительность запроса в секундах, число входных и выходных токенов. Если провайдер не сообщает токены, укажите `null`. Секретные ключи в результаты не включаются.

## 3. Папка кейса

```text
task/
├── task.toml                # Метаданные, списки тестов, лимиты
├── instruction.md           # Задание для AI, который будет решать кейс
├── environment/
│   ├── Dockerfile           # Воспроизводимое окружение
│   ├── requirements.txt     # Зависимости, если нужны
│   └── repo/                # Стартовый код задачи
├── tests/
│   ├── test.sh              # Запуск проверок и запись результата
│   └── ...                  # Тесты и необходимые им данные
└── solution/
    ├── solve.sh             # Применение эталонного решения
    └── ...                  # Дополнительные файлы решения, если нужны
```

Смотрите реальные файлы в [example-case/](example-case/). Пример посвящён проверке числового интервала и показывает формат; задание по банковскому проекту находится во входном JSON.

`instruction.md` описывает цель, ожидаемое поведение и ограничения. Он не содержит готовую реализацию, имена скрытых тестов или ссылки на эталонное решение. AI-разработчику доступны только задание и `environment/repo/`. Тесты из `tests/` и файлы из `solution/` ему недоступны.

В папке кейса не должно быть логов прогонов, кэшей, виртуальных окружений, истории Git и локальных результатов сборки. Зависимости и ресурсы для работы проекта допускаются в `environment/`.

## 4. Манифест task.toml

Полный заполненный образец: [example-case/task.toml](example-case/task.toml).

Обязательные поля:

- В корне: `schema_version = "1.1"`.
- `[task]`: `name` (входной `case_id`), `description`, `authors = [{ name = "…", email = "…" }]`.
- `[metadata]`: `task_type = "agentic"`, `bank_domain` (предметная область задачи), `language`, `build_tool = "docker"`, `difficulty`, `source`, `team`, а также три массива тестов, описанные ниже.
- `[agent]`: `timeout_sec`.
- `[verifier]`: `timeout_sec`.
- `[environment]`: `allow_internet = false`, `build_timeout_sec`, `cpus`, `memory_mb`, `storage_mb`.

Лимиты и сведения об авторе берутся из входа. Имя и email автора сохраняются в манифесте.

Три массива содержат полные идентификаторы тестов pytest, например `tests/test_interval.py::test_right_boundary`:

- `fail_to_pass`: каждый тест падает на исходном коде и проходит после корректного решения;
- `pass_to_pass`: каждый тест проходит до и после решения, защищая существующее поведение;
- `anti_cheat`: каждый тест проходит до и после решения, проверяя объявленные в задании ограничения.

Каждый собранный pytest тест должен входить ровно в один список. Параметризованные варианты перечисляются полностью. Pytest служит единым внешним интерфейсом проверки; сами тесты могут запускать SQL в PostgreSQL или код на других языках.

## 5. Исполнение и требования к приёмке

1. Docker-образ собирается из `environment/`. Все зависимости устанавливаются при сборке. Стартовый код размещается в `/app/repo`. Скрытые тесты и эталонное решение в образ не копируются.
2. При проверке `tests/` монтируется read-only в `/tests`, каталог результатов — в `/logs`. При проверке эталона `solution/` дополнительно монтируется read-only в `/solution`. Проверка работает без внешней сети.
3. `tests/test.sh` записывает одну строку `0` или `1` в `/logs/verifier/reward.txt`. Значение `1` означает, что все обязательные проверки прошли. Логи хранятся отдельно. Ошибки, пропущенные тесты и неполное выполнение не считаются успехом.
4. На исходном коде reward равен `0`: все `fail_to_pass` падают по причине несоответствия поведению из задания; все `pass_to_pass` и `anti_cheat` проходят. Ошибка импорта или окружения не заменяет проверку дефекта.
5. После `solution/solve.sh` на отдельном свежем экземпляре окружения все тесты проходят и reward равен `1`. Скрипт решения исправляет код, не меняет тесты и не записывает reward.
6. Каждый из трёх списков дополнительно проверяется отдельно на исходном и исправленном коде. Независимый повтор полного прогона воспроизводит исходы. `skip`, `xfail` и отсутствие ожидаемых тестов не принимаются.
7. Проверки оценивают заявленное поведение и принимают альтернативные корректные реализации. Все проверяемые ограничения указаны в задании.
8. Сведения о выполнении и использовании LLM сохранены в `evidence/`. Исходный репозиторий не изменён.

Команды сборки и запуска полного кейса приведены в [README примера](example-case/README.md).

## 6. Критерии оценки

- Автоматическое создание полноценного кейса по входным параметрам.
- Качество проверок: воспроизведение дефекта, принятие корректного решения, обнаружение ошибок и нарушений ограничений.
- Повторяемость результата, диагностика сбоев и сохранность исходников.
- Работа с большим проектом и связанным кодом Python и SQL.
- Расход LLM и удобство запуска программы.
